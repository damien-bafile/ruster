# Compositor Verification Matrix

The Phase 0 Wayland compositor's acceptance criteria and how to check each one.
This page is the manual test plan for the `ruster-compositor` crate — see
[windows.md](windows.md) and [keybindings.md](keybindings.md) for the rest of
the platform and key documentation.

## The matrix

| Criterion | Check |
| :--- | :--- |
| Workspace builds | `cargo build` |
| All crates test clean | `cargo test` |
| Clippy clean | `cargo clippy --all-targets` |
| Shell state unit tests | `cargo test -p ruster-shell` |
| Render-gles unit tests | `cargo test -p ruster-render-gles` |
| Winit compositor boots | `just compositor` |
| Client maps & composites | `just compositor` + auto-launched `foot` |
| Titlebar chrome updates on focus | focus `foot`, title shows in statusline |
| Lua keybinds work | `M-t` cycles WS label; `M-S-q` quits |
| Editor frame + which-key visible | visual check at 1080p |
| DRM boots (hardware) | `just compositor-drm` on a free VT |
| SIGINT quits cleanly | `Ctrl-C`, process exits 0 |

## Results on this machine

Run nested under a Wayland session (`mango`, NVIDIA RTX 4090, GLES 3.2), on a
`1873x1334` winit window. The DRM rows still need a free VT and are not covered
here.

An earlier pass of this table was recorded on a headless box and marked every
display row ⛔ "not run". Those rows were the ones hiding the bugs: the first
time the compositor was actually put on a screen it rendered upside down, drew
no client at all, and killed its own client on startup. Later, the first time a
key was actually pressed, it turned out the Lua config could not bind anything —
the matcher recognised two hardcoded strings and discarded the configured action
name. Treat a ⛔ here as an untested claim, not a passing one.

Note on driving the nested compositor: `wtype` cannot do it. It uploads its own
xkb keymap to the *host*, and a nested compositor receives raw keycodes which it
resolves with its own keymap, so keysyms arrive scrambled — typing `echo hello`
into the nested client produces `12342555553678396`. Injecting on a virtual
evdev device instead makes the host see an ordinary keyboard and forward
ordinary keycodes.

Resize now calls `request_redraw` like everything else. `RedrawGate` is a type rather than a bool so this stays a single chokepoint, and its tests assert an invitation is consumed by one frame and that repeated invitations do not accumulate |
| The compositor can trigger an action on a delay | `ruster.wm.defer(ms, "action")` in `compositor.lua` | ✅ the same action vocabulary as a keybind, later. This is what made the row above possible: a config is read before the first frame, which is far too early to photograph anything that needs a round trip — rust-analyzer took **19.7s** on a cold crate to answer, and a 6s delay caught an empty gutter that looked exactly like a broken one. Deferred actions run after the immediate queue on the pass their deadline falls in, and same-instant actions keep their scheduling order, because `defer(0, "edit")` then `defer(0, "screenshot")` means "then". A `screenshot` deferred while the host is not presenting is not lost — it waits for the next real frame, since the capture lives inside the render |
| The idle loop sleeps instead of spinning | `SIGSTOP` the host weston so it stops presenting, diff `/proc/<pid>/stat` ticks over 10s | ✅ **0 ticks over 10s**, parked in `do_epoll_wait`, against 23 on the 1ms timeout the gate fix left behind. `SIGCONT` brings it back to 118 ticks/s. Winit is a calloop source now, so the loop blocks on its sources rather than polling — the same shape niri and Hyprland use. `poll_timeout` returns `None` unless something with no fd needs a clock: a running language server (mpsc channel, 16ms), a half-typed chord (250ms), or a pending `ruster.wm.defer` deadline. Five mutations planted, all killed |
| Blocking does not cost frame rate | same weston harness, `RUSTER_BENCH_GLYPHS` | ✅ a locked **60–61 fps at ~3.4ms/frame**. The first attempt at the back-off was a heuristic guessing whether the host was still presenting, needed only because winit was pumped by hand and its timeout therefore bounded input latency. At a 16ms boundary it cost a quarter of the frame rate — **41–50 fps**, because at 60Hz the gap between invitations straddles the boundary, so the loop kept dropping into its idle cadence and missing frames. Registering winit with calloop deleted the tradeoff rather than tuning it |
| Quit takes effect while the host is not presenting | `ruster.wm.defer(12000, "quit")`, `SIGSTOP` weston at 3s | ✅ exits at **12.0005s** with the host still stopped. Blocking indefinitely introduced this and nothing else would have caught it: the deferred quit fired on time and set `running = false`, then the loop went back to sleep — the `while` condition is only reached after the dispatch returns — and the process sat alive for another 13s until an unrelated event woke it. `pump` now refuses to sleep once `running` is false. Signals were never affected; those come through calloop's own source |
| The launcher opens and filters | `M-space`, then type | ✅ **seen, not inferred.** `Super+Space` opens an overlay; typing `fi` narrowed 74 desktop entries to Files, Firefox and Foot Client, each with its description in grey and the first row highlighted. `docs/verification/compositor-launcher-apps.png`. | A client can read the screen (`wlr-screencopy`) | `grim` against ruster's own socket | ⛔ **the protocol talks, the pixels are unproven.** smithay 0.7 does not implement this, so the handlers are ours and only the bindings are generated. `grim` binds the global, accepts the `buffer`/`buffer_done` it is offered, allocates, and sends `copy` — each of those is a step it refused before the one behind it was fixed. It found a real defect on the way: screencopy offered `Xbgr8888` while `wl_shm` advertised only its two guaranteed formats, so the compositor answered its own offer with `format Xbgr8888 not supported`. **What has never run is the copy itself** — serving it needs a rendered frame, the host was blanked by then, and the capture timed out exactly as designed (`no frame was rendered in time`, twice). A capture now calls `request_redraw` rather than waiting for a frame to wander past, which is the compositor's job and not the client's, but that only helps a host that is presenting at all. | Screenshot costs a frame | capture nested, watch the log | ⚠️ every capture is followed by one `Failed to submit buffer: The context has been lost`; the PNG is correct. A one-frame stutter, as recorded |
| A screenshot that cannot be taken says so | ask for one under a host that is not presenting the window | ✅ **and the first diagnosis of this was wrong.** The silence after a capture looked like a wedged event loop, so the loop was instrumented with `toggle help` — which dispatches from the timer rather than the render pass — and it turned out to be **perfectly healthy**: four actions on time, a deferred quit at 15s, and *no capture at all*, no PNG, no EGL error, no log. The redraw gate was working exactly as designed. Rendering waits for the host to invite a frame; a nested window that is occluded or on another workspace is never invited; and `screenshot` only sets a flag the render pass consumes, so it dispatched into that silence and reported success. `screenshot_pending` is now the *time* of the request, and a capture still waiting after two seconds is given up on with a warning naming the reason — measured at `waited_ms=2000`. | DRM pointer (libinput) | move a mouse | ✅ confirmed on hardware: the cursor is visible and follows the mouse, and `pointer button` events reach the seat. Relative motion had never executed anywhere — winit only sends absolute — and nothing logged it, so a boot could not report whether the mouse did anything; it now traces `dx`/`dy` at trace level, quiet enough not to drown the log the way the paused render loop did |
| Cursor is drawn | move the pointer over chrome, then over a client | ✅ nested: the built-in arrow renders over chrome, and a client's own cursor surface (foot's I-beam) renders with its hotspot applied once the pointer enters it |
| `Ctrl+Alt+F<n>` switches VT | press it on a DRM boot | ✅ **fixed, then confirmed on hardware.** Pressed on hardware, it did nothing: the log shows `key=F2 modified=XF86Switch_VT_2`, and the handler was testing the *raw* sym, which is plain `F2` and never in the `XF86Switch_VT_*` range. So VT switching had been dead since it was written. The old test called `vt_switch_target(Keysym::XF86Switch_VT_2)` directly — an input the real code never produced — and passed throughout. Now reads the modified sym, guarded by a test that drives Ctrl+Alt+F2 through the real seat and asserts the session was asked for VT 2, and confirmed on hardware: `switching virtual terminal vt=2` with the compositor still alive afterwards |

| DRM hands the device back cleanly on exit | quit and check the log | ✅ confirmed on hardware: `released the drm device`, zero `Failed to restore previous state`, clean teardown. Error: Invalid argument`. smithay's atomic `Drop` replays every property captured at startup in one commit — connectors, CRTCs, framebuffers, planes — and the kernel rejects it, almost certainly because the capture includes immutable properties (a connector's EDID and PATH among them) and an atomic commit that sets one is invalid by definition. Nothing is lost: the restore never once succeeded, so the behaviour observed all along *was* the no-restore behaviour, and dropping master is what the console driver actually waits for. The error is gone because the commit is no longer attempted |

## Running the real thing

```bash
# Winit (nested, dev): boots a window on a running display server.
just compositor

# DRM (hardware): needs a free VT and seatd/logind access. Builds, logs to
# /tmp/ruster-drm.log, and reports what happened once it exits.
just compositor-drm
```

The `just compositor` / `just compositor-drm` recipes are defined in the root
`justfile`. The first is `cargo run -p ruster-compositor`; the second runs
`scripts/drm-test.sh`, which builds with the `udev` feature, launches on DRM,
and afterwards reports the exit status, any screenshots and whether a VT switch
was seen — on a VT that summary is the whole diagnosis, since the screen is gone
by the time you can read anything.
